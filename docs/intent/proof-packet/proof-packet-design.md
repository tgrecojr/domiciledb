# Proof packet

## Context and Design Philosophy

The proof packet is the headline output. Everything else in DomicileDB exists so that, after a
fire, flood, or theft, the owner can hand an adjuster one document that proves what they owned and
what it was worth. The packet is therefore judged by the adjuster's standard, not the owner's:

- **Organized the way a claim is reviewed**: by room, with a household summary first, totals by
  room and by category, and the coverage position stated plainly.
- **Evidence-forward**: photos next to each item, make / model / serial, condition and age,
  purchase and replacement values, and what documents are on file.
- **Honest about gaps**: unvalued items are listed but excluded from totals, and the summary says
  how many.
- **Print-ready and self-contained**: a PDF with no external dependencies, generated on demand
  for the whole household or one room or one category.

The packet is a pure projection. It owns no data of its own; it reads items, photos, documents,
valuations, locations, and the coverage summary, and it must never disagree with the dashboard
about the same items.

## Assembly

`getReportPacket(householdId, filter?)` (`src/lib/queries/report.ts:40-163`) runs four to six
batched queries: items left-joined to category, optionally filtered by `locationId` or
`categoryId` (both may combine); photos per item ordered by `sort_order` then id, like the item
page; documents per item with their stored paths; the latest `price_paid` valuation
per item (max `valued_at`, string compare); location names; room photos for locations present in
the filtered set; the household row; and a fresh `getCoverageSummary`. It labels the filter
"Entire household", "Location: <name>", or "Category: <name>" (`:147-153`) and stamps
`generatedAt`.

`assembleReport({ items, locationNames, locationPhotos })` (`src/lib/report.ts:71-132`) is pure:

- Keeps only `lifecycleStatus === "active"`; `itemCount` is the active count (`:77, 130`).
- `itemAggregateCents` delegates to the coverage module's `itemValueCents` (cost × sanitized
  quantity, clamped to the safe-integer range), and every total is accumulated with its
  `addCents`, so the packet and the dashboard share one arithmetic.
- Groups into rooms by `locationId`; a null or unknown id becomes the "Unassigned" room
  (`:62, 88-91`). Each room totals its valued items; unvalued items stay listed and increment
  `excludedCount` (`:101-103`).
- `categoryTotals` by category name, null → "Uncategorized", sorted by cents descending
  (`:108, 120-122`).
- Rooms sort by name with "Unassigned" forced last; items keep input order (`:114-118`).
- Room photos attach only to rooms with a real `locationId` (`:92-95`).

For the unfiltered household the grand total equals the dashboard's coverage total: both read
`item.current_replacement_cost × quantity` over active items.

## The document

`renderProofPacket(packet)` (`src/lib/pdf/render.tsx`) first loads at most 4 photos per item and
4 per room from `pathOriginal`, downscaled to 600 px JPEG at quality 80, one at a time to bound
memory; a missing or corrupt photo is skipped and the item still renders (`render.tsx:9-31`;
`images.ts:29-46`). WebP web variants cannot be embedded by react-pdf, hence the originals.

`ProofPacketDocument` (`src/lib/pdf/proof-packet.tsx`), Letter, Helvetica 9 pt:

```
┌─────────────────────────────────────────────────────┐
│ <Household> — Home Inventory        Proof-of-loss   │ ← running header
│                                                     │
│ Home Inventory                                      │
│ <Household name> · <address>                        │
│ Generated Oct 24, 2026 · Entire household           │
│ ┌─────────────────────────────────────────────────┐ │
│ │ $310,000.00                                     │ │ ← summary box
│ │ 42 valued · 3 not yet valued · 45 active items  │ │
│ │ Coverage B limit $456,750.00  [Within · 68%]    │ │ ← pill
│ └─────────────────────────────────────────────────┘ │
│ Totals by category                                  │
│   Electronics ............................ $xx,xxx  │
│ Informational only — verify with your insurer.      │
│ Generated by DomicileDB · Informational only   1/7  │ ← footer
├─────────────────────────────────────────────────────┤
│ Inventory by location                               │ ← first room page only
│ Living room                              $xx,xxx    │ ← room header (+ "(cont.)")
│ [room photo] [room photo]                           │ ← first page of a room only
│ ▸ Sony TV ............................ $2,000.00    │
│   Category · Manufacturer · Model · Serial · Qty    │
│   Condition · Age · Price paid $1,500 (Mar 3, 2024) │
│   [photo][photo][photo][photo]                      │
│   Receipts [receipt img][receipt img]               │
│   Attached: receipt (invoice.pdf), warranty (w.jpg) │
│ … up to 10 items per page …                         │
└─────────────────────────────────────────────────────┘
```

Rules with evidence: the coverage line reads "No Coverage B limit on file." when there is no
policy, limit, or status, otherwise "Coverage B limit $X" and a colored pill "Within coverage |
Approaching limit | Over limit · N%" (`proof-packet.tsx:23-27, 118-142`). Rooms are chunked at
`ITEMS_PER_PAGE = 10` with continuation chunks flagged; rooms with no active items yield no page
(`paginate.ts:9, 20-26`). Item blocks show Quantity only when > 1 and "Replacement (each)" only
when quantity > 1 and valued. Up to two receipt images per item (`receiptCandidates` in
`pdf/receipts.ts`: kind `receipt` with an image extension, in attachment order) are embedded
beneath the photos, loaded and downscaled like photos; every document is then listed as
`kind (filename)`, so PDF receipts and warranties are named even though they are not rendered
(`proof-packet.tsx`, `render.tsx`). An empty inventory renders "No active items to report." (`:207-213`). Dates are en-US
short month; invalid dates print "—" (`:12-21`). Metadata: title "<household> — Home Inventory",
author "DomicileDB" (`:155-158`).

## Route and page

`/report` (`src/app/report/page.tsx`) is a link page: "Download entire household", one link per
location (when any exist), one per category, each pointing at `/api/proof-packet` with the
matching query. The page counts the household's active items first; above
`PROOF_PACKET_MAX_ITEMS` it replaces the whole-household link with a notice stating both numbers
and pointing at the narrower packets, so the owner is never offered a download the route will
refuse. `GET /api/proof-packet` (`src/app/api/proof-packet/route.ts`) accepts
`?location=` and `?category=` as positive integers only, returns 404 without a household, 413 with
"narrow with ?location= or ?category=" when `itemCount > PROOF_PACKET_MAX_ITEMS` (default 2000,
VULN-010) before rendering, and otherwise streams `application/pdf` as
`home-inventory-YYYY-MM-DD.pdf` (date from `generatedAt`) with `Cache-Control: no-store`.

The backup job (resilience) renders the same packet for the household with no filter and uploads
it as `backup/proof-packet-latest.pdf`.

| Output format           | Print-ready PDF                                                                                                        | HTML print view; spreadsheet; JSON       | Spec §8: a polished PDF is the v1 priority; structured export is explicitly later.                                                                                                                                                            |
| Renderer                | `@react-pdf/renderer` (pure JS)                                                                                        | Headless Chromium; LaTeX; pdfkit by hand | architecture.md: no browser binary keeps the distroless image slim; React components reuse the team's one language.                                                                                                                           |
| Organization            | By room, summary first, totals by room and category                                                                    | By category; flat list                   | Spec §8: adjusters walk a loss room by room; categories matter because policies think in categories.                                                                                                                                          |
| Which items             | Active only                                                                                                            | All with a lifecycle note                | Spec §7/§8: the packet is the claim picture; sold items would inflate it.                                                                                                                                                                     |
| Unvalued items          | Listed, excluded from totals, counted                                                                                  | Omitted; counted at $0                   | Spec §7: "at least $X"; principle 6 keeps drafts in the record.                                                                                                                                                                               |
| Pagination              | Explicit 10-item chunks per room                                                                                       | react-pdf auto-wrap                      | `paginate.ts:4-7`: auto-pagination is O(n²) and overflowed yoga past ~80 items.                                                                                                                                                               |
| Photos per item / room  | First 4 of each                                                                                                        | All; 1                                   | Four thumbnails fit a row at 70 px and bound render time and PDF size; the first photos are the capture shots.                                                                                                                                |
| Photo source            | Originals, downscaled to 600 px JPEG                                                                                   | Web WebP variants                        | `images.ts:9-12`: react-pdf does not embed WebP.                                                                                                                                                                                              |
| Image loading           | Sequential, failures skipped                                                                                           | Parallel; fail the packet                | `render.tsx:12`: memory control; a missing photo must not block the claim document.                                                                                                                                                           |
| Documents in the packet | Up to two receipt images embedded per item; every document listed as kind (filename)                                   | Kinds only; rasterize PDF receipts too   | Spec §8 calls the packet photo-and-receipt-backed, and a receipt image next to the item is the proof an adjuster asks for first. PDF receipts are named, not rendered: rasterizing PDFs needs a renderer the distroless image does not carry. |
| Size guard              | Route refuses above `PROOF_PACKET_MAX_ITEMS` with narrowing guidance; the report page withholds the link above the cap | Render anyway; paginate the download     | VULN-010: a giant packet is a memory and CPU denial-of-service on a single-user box; location and category filters already exist, and the page should not offer what the route refuses.                                                       |
| Totalling arithmetic    | Consumed from the coverage module (`itemValueCents`, `addCents`)                                                       | Own implementation                       | The packet must never disagree with the dashboard; one owner for the rule.                                                                                                                                                                    |
| Photo order             | `sort_order` then id, the item page's order                                                                            | Insertion order                          | The first photos in the packet should be the ones the owner sees first on the item.                                                                                                                                                           |
| Caching                 | `no-store`, generated per request                                                                                      | Cache the latest PDF                     | The packet must reflect the current inventory; the only stored copy is the backup's, which is refreshed on each run.                                                                                                                          |
| Serial numbers          | Printed in full                                                                                                        | Masked                                   | Serials are the proof; masking defeats the document's purpose. The PDF is treated as sensitive (no-store, S3 only under the operator's bucket).                                                                                               |

## Open Questions & Future Decisions

### Resolved

1. ✅ Structured/spreadsheet export is not v1 (spec §10); the ZIP export in resilience covers
   data portability.
2. ✅ Receipt images are embedded (two per item); PDF receipts are listed by filename
   (PACKET-PDF-011).
3. ✅ The coverage module owns the per-item value and clamped addition; the packet consumes them
   (PACKET-DATA-002, PACKET-DATA-012).
4. ✅ Packet photos follow the item page's order (PACKET-DATA-009).
5. ✅ The report page withholds the whole-household link above the item cap (PACKET-ROUTE-005).

### Deferred

1. **Rasterizing PDF receipts** would need a PDF renderer in the runtime image; revisit if a
   pure-JS option becomes acceptable.
2. **Latest price paid.** Lexicographic max on `valued_at` mixes `YYYY-MM-DD` purchase dates with
   full timestamps; compare as dates.
3. **"Unassigned" collision.** A real location named "Unassigned" shares the label and the
   sort-last rule.
4. **Category label fallback** "Category: Selected" when the filtered set is empty.
5. **Unit coverage of rendering.** Both route tests mock the renderer; only e2e asserts a real
   PDF. Consider a renderer smoke test on a small packet.
